# Lesson 30 — Rapid-fire master Q&A

> **How to use this:** cover the answer column. Say your answer **out loud**, then compare. Anything you got wrong or hedged on goes into `RECALL.md`, and you re-test those every Sunday, cold. Recognition feels like knowledge and isn't — the only useful signal is whether you can *produce* the answer under pressure.
>
> **Answers are compressed here on purpose.** They're the shape of a strong answer, not the full explanation; the lesson reference has the depth. Target: ~40 seconds spoken per answer, with a reason attached to every claim.

**Time:** ~2 h for a full pass · ~30 min for a re-test

---

## How answers are scored

Every question has three answer levels. Aim for level 3 consistently.

| Level | Sounds like |
|---|---|
| **1 — Recall** | The definition. "PUT replaces, PATCH updates." |
| **2 — Mechanism** | *Why* it works that way, and what breaks otherwise |
| **3 — Judgement** | Level 2 + the trade-off + what you'd actually do + what would change your mind |

## Part 1 — HTTP & foundations (30)

| # | Question | Strong answer |
|---|---|---|
| 1 | What is an API? | A contract letting one component depend on another's behaviour without its implementation, so both change independently. Four layers: syntax, semantics, operational guarantees, lifecycle. Most production bugs are in layers 2–3. [L01] |
| 2 | Safe vs idempotent vs cacheable? | Safe = read-only intent. Idempotent = N calls have the same effect as 1. Cacheable = the response may be stored. Safe ⇒ idempotent. `PUT`/`DELETE` are idempotent but not safe. `POST` is none — hence idempotency keys. [L03] |
| 3 | Is `DELETE` idempotent if the 2nd call 404s? | Yes — idempotency is about **effect on state**, not response equality. I'd return 204 both times so a retried delete doesn't surface as an error. [L03] |
| 4 | `PUT` vs `PATCH` vs `POST`? | The pivot is **who owns the URI** and **totality**. `POST /payments` — server assigns the ID, not idempotent. `PUT /payments/pi_1` — client names it, full replacement (omitted fields cleared), idempotent, upsert. `PATCH` — partial, format undefined by HTTP so pick merge-patch. [L03, L09] |
| 5 | Why is `PUT` "not update"? | It means "make this URI's resource exactly this." Omitted fields must be **cleared**. If your handler only touches present fields, you built `PATCH` and named it `PUT` — and clients clearing a field by omission fail silently. [L09] |
| 6 | 401 vs 403? | 401 = unauthenticated (retry with credentials; must send `WWW-Authenticate`). 403 = authenticated but not permitted (retrying is pointless). Names are historically backwards. [L03] |
| 7 | 400 vs 422? | 400 = can't parse/structurally wrong. 422 = parsed, semantically invalid. Pragmatically the distinction buys clients little since they branch on `code`; pick one and be consistent. Stripe uses 400 broadly; GitHub uses 422. [L10] |
| 8 | 409 vs 412? | 412 = a precondition **you supplied** failed (`If-Match`) → re-read and retry. 409 = conflicts with current state regardless of preconditions → retrying unchanged never works. [L09] |
| 9 | 403 or 404 for another tenant's resource? | 404 when existence is sensitive — for tenant data, always — because 403 confirms existence and enables enumeration. 403 when the caller legitimately knows it exists but lacks permission for that action. GitHub 404s private repos. [L10, L15] |
| 10 | What's `202 Accepted` for? | Work outliving the request. Return 202 + a job resource (`Location`), then the client polls, or you webhook them, or stream via SSE. Anything over ~2s should not be a synchronous request. [L03] |
| 11 | Never return 200 with an error body — why? | Every LB, CDN, retry library, dashboard and alert branches on status. `200 {"success":false}` makes your error rate read 0%, defeats retries, and forces every client to parse bodies to detect failure. [L03, L10] |
| 12 | What is a payload? | Body + the headers describing it (HTTP/1.1 term); RFC 9110 renames the decoded data "content". Practically: the body. The point is that the **operational contract lives in headers**, not the body. [L04] |
| 13 | How does the receiver know where the body ends? | `Content-Length`, or `Transfer-Encoding: chunked`, or HTTP/2 frame lengths. Ambiguity between the first two is the **request smuggling** class. [L04] |
| 14 | `Accept` vs `Content-Type`? | `Accept` = what I want back. `Content-Type` = what this message's body is. Both can appear in one request, opposite directions. [L04] |
| 15 | What does `Vary` do? | Declares which request headers change the response. Omit it while varying on `Authorization` or `Origin` and a shared cache serves one user's data to another. **Security bug, not a perf bug.** [L04, L17] |
| 16 | Walk me through an API call. | 12 stages: URL parse → cache check → HSTS/CORS decision → service worker → connection reuse → DNS → TCP (1 RTT) → TLS (1–2 RTT) → request → kernel queue/LB/gateway → app pipeline → response → CORS check/cache write → parse. **6–8 are skipped on a warm connection** — which is why call #2 is 10× faster. [L02] |
| 17 | What is CORS protecting, and who enforces it? | The **browser** enforces it, protecting the *user* from a malicious page reading their authenticated data elsewhere. Not a server-side control — which is why "works in Postman, fails in browser" means CORS. [L02] |
| 18 | What triggers a preflight? | Anything non-"simple" — which includes `Content-Type: application/json` or an `Authorization` header, i.e. essentially every real API call. Mitigate with `Access-Control-Max-Age`. [L02] |
| 19 | Why does a cross-origin POST still execute even when the browser blocks the response? | For simple requests the browser sends it, the server processes it (side effects included), then withholds the response from JS. So a request that "failed" may have charged the card. [L02] |
| 20 | Why must CORS come before auth in middleware? | Preflights carry no credentials; auth-first returns 401 to `OPTIONS` and every browser call dies. Also rate-limit before auth so attackers don't get free crypto work. [L02] |
| 21 | Why is the first request slow and the rest fast? | Cold DNS + TCP + TLS = 3 RTTs, plus possibly a cold container, empty cache, and lazy pool init. All skipped on reuse. Don't just say "caching" — name the stage. [L02] |
| 22 | Does HTTPS hide the URL? | Path and query are encrypted; **the hostname isn't** (SNI + DNS). And the path still lands in your logs, the CDN's, and browser history. Hence: no secrets in URLs. [L02, L04] |
| 23 | `ECONNREFUSED` vs `ECONNRESET` vs `ETIMEDOUT`? | Nothing listening / peer killed an established connection / packets vanished. Intermittent RESET under load usually means an LB↔app idle-timeout mismatch. [L02] |
| 24 | HTTP/1.1 vs 2 vs 3? | 1.1: ~6 connections/origin, head-of-line blocking. 2: one connection, multiplexed streams, HPACK. 3: QUIC over UDP, no TCP head-of-line blocking — better on lossy mobile. HTTP/2's single connection is worse than 1.1's six under heavy packet loss. [L02] |
| 25 | Why did JSON beat XML? | JSON is the browser's native data model — parsing was free when AJAX exploded; that's what decided it. Also 30–50% smaller, and one obvious way to express a value vs XML's attribute-or-element ambiguity. But XML is a *document* format repurposed for data; it's still right where namespaces, formal schemas, signatures or transformations matter. [L05] |
| 26 | JSON's limitations? | Number precision (the big one), no date type, no binary, no native schema, spec ambiguities (duplicate keys, `undefined` vanishing, `NaN`→`null`). Lead with numbers and cite Twitter's `id_str`. [L05] |
| 27 | How do you represent money? | `{amount_minor: 4999, currency: "usd"}` — integer minor units + ISO 4217. Follow-ups: JPY has 0 decimals and BHD has 3, so **you need the currency to interpret the integer**; for fractional units use a decimal string + explicit scale. [L05] |
| 28 | Why send large IDs as strings? | `Number.MAX_SAFE_INTEGER` is 2^53−1. Beyond it, JS silently loses precision, so a 64-bit DB ID becomes a *different* ID after a round trip. Silent corruption. [L05] |
| 29 | How do you handle timezones? | Store and transmit UTC, ISO 8601 with `Z`, fields named `*_at`. Store the user's **IANA zone name**, not an offset, because offsets change with DST. For future recurring events store local time + zone, or the meeting moves. [L05] |
| 30 | Protobuf vs JSON? | ~3× smaller, 3–5× faster: field numbers instead of names, varints, no text parsing, mandatory schema. Cost: not human-readable, needs codegen, browsers need a proxy. "JSON at the edge, Protobuf inside." [L05, L22] |

## Part 2 — REST & design (35)

| # | Question | Strong answer |
|---|---|---|
| 31 | What is REST? | Six constraints — client–server, statelessness, cacheability, uniform interface, layered system, optional code-on-demand — chosen to induce scalability and independent evolvability. Not a protocol or a URL style. Most "REST APIs" are Richardson Level 2. [L06] |
| 32 | What does statelessness mean? Isn't a DB state? | It's about **client session state**, not resource state. What it buys: any instance serves any request → horizontal scaling, painless deploys, crash resilience. [L06] |
| 33 | So JWTs are stateless and sessions aren't? | JWTs move session data to the client — genuinely stateless verification. You pay in revocation. A Redis session store isn't purist-stateless but preserves the property that matters (any instance can serve any request) with trivial revocation. Not dogma either way. [L06, L13] |
| 34 | What's HATEOAS? Do you use it? | Clients discover transitions from links, not hardcoded URLs — the constraint that makes something Level 3. Nearly nobody implements it fully because real clients branch on status. But two hypermedia patterns *are* universal and I do use them: **pagination cursors** and `Location` on 201. [L06] |
| 35 | Richardson maturity levels? | 0: one endpoint, tunnel. 1: resources. 2: verbs + status codes ← where the industry lives. 3: hypermedia. Level 2 done well is the practical maximum. [L06] |
| 36 | Is GraphQL RESTful? | No — one endpoint, POST for reads, no resource identity, no HTTP caching, opaque to intermediaries. Level 0 by Richardson, deliberately, because it optimises a different variable. [L06, L21] |
| 37 | Is `POST /users/123/deactivate` RESTful? | Strictly no, and it's still the right choice: deactivation has side effects a field-set doesn't convey, can carry a reason code, and can be permissioned separately from profile edits. Level 2 with a documented exception. [L06, L07] |
| 38 | How do you find resources from a requirement? | List the nouns the *domain* uses, then ask per noun: does it have identity, a lifecycle, and would anyone list/filter/link to it? And resources aren't tables — one resource can span tables, one table can surface as three resources, and some resources have no table. [L07] |
| 39 | URL rules? | Plural nouns, lowercase with one separator convention, max one nesting level, version leftmost, path identifies / query filters, verbs only as a last segment on POST, opaque prefixed non-sequential IDs, no extensions, no trailing slash. **Test: after 3 endpoints can someone guess the 4th?** [L07] |
| 40 | `/users/123/orders` or `/orders?user=123`? | Both: nest to **create** (parent is required context), flat + filter to **list** (composable with other filters, which nesting can't do). [L07] |
| 41 | How deep should nesting go? | One level, two exceptionally. Deeper means validating the whole chain — which you'll forget, and that's an authz bug. The child usually has a globally unique ID anyway. [L07] |
| 42 | Why not sequential integer IDs? | Enumeration (→ real breaches), business-intelligence leakage (competitors diff your IDs to learn your volume), and no offline/sharded generation. Use ULID/UUIDv7 with a type prefix. [L07] |
| 43 | Three ways to model an action? | (a) Model the result as a resource (`POST /payments/{id}/refunds`) — **check this first**; (b) verb sub-path for a pure transition (`/cancel`); (c) `PATCH` a field only if it's genuinely inert. Rule: does it produce something worth keeping? [L07] |
| 44 | Design `GET /payments` for 4M rows. | Cursor pagination (O(1) vs O(offset)), composite index with `merchant_id` leading and a unique tiebreaker, `limit+1` for `has_more`, allowlisted filters and sorts, `total_count: null`, tenancy from the token. **Then volunteer the drift problem.** [L08] |
| 45 | Why not offset pagination? | Two independent failures: **O(offset)** scan cost (page 200k of 4M ≈ 20s), and **drift** — concurrent inserts cause duplicates, deletes cause silently skipped rows. Drift is the worse one: it's a correctness bug. [L08] |
| 46 | Why must a cursor have a unique tiebreaker? | A non-unique sort column gives non-deterministic order, so cursor pages duplicate and skip rows. Always `ORDER BY sort_col, id` and compare both. [L08] |
| 47 | Why are cursors opaque? | So clients can't construct them, which keeps the scheme changeable (Hyrum's Law). And composite keys need a container anyway. **Tenancy never lives in the cursor** — a forged cursor must only ever return the caller's own data. [L08] |
| 48 | PM wants an exact total count of 4M rows. | Push back: it's a second full scan on your hottest endpoint to satisfy a number nobody acts on — the user's next action is "search" or "load more". Offer `has_more`, or an approximate count labelled as approximate, or exact only when the filtered set is under a threshold. [L08] |
| 49 | 40 filters that exceed URL length? | `POST /payments/search` with a body, documented as a deliberate exception (not cacheable, non-safe method for a read). Fully-RESTful alternative: a saved-search resource — `POST /searches` → `GET /searches/{id}/results`, which is cacheable, shareable and re-runnable. [L08] |
| 50 | How do you prevent a lost update? | Optimistic concurrency: `ETag` on GET, `If-Match` on write, 412 on mismatch — **with the version predicate inside the `UPDATE … WHERE`**, not a separate read. Then pessimistic locks for short server-side critical sections, and **design it away** with append-only entries where possible. [L09] |
| 51 | How do you make `PATCH` idempotent? | Require `If-Match`: the first apply bumps the version, so the retry's stale ETag gets 412 instead of applying twice. Or an idempotency key, or replacement-style rather than relative semantics. [L09] |
| 52 | Which PATCH format? | JSON Merge Patch (`application/merge-patch+json`) as the default: present = set, `null` = clear, absent = unchanged, objects merge, arrays replace. JSON Patch when you need array ops or `test`. Ad-hoc works but you must document `null` handling and nested merge behaviour. [L09] |
| 53 | Client sends `{"phone": null}` — what does it mean? | Under merge-patch: clear the field. If your schema rejects null, clients have **no way to clear an optional field** — a real functional gap. And `JSON.stringify` drops `undefined` entirely, so "absent" and "null" must be distinguished with `in`, not truthiness. [L09] |
| 54 | Design a bulk create for 10,000 records. | Async: `POST` → 202 + job resource → poll or webhook → per-item error report. Cover per-item idempotency (a retry mustn't duplicate the 9,987 that succeeded), per-item rate metering, size caps, and file/streamed input. Sync cap ~100 items. [L09] |
| 55 | Half a bulk operation failed. Status? | `207 Multi-Status` with per-item statuses — never 200. **And echo the input index per item**, or the client can't correlate results to inputs. [L09] |
| 56 | Design an error response. | Frame it by the **four audiences**: the client's code (stable `code` + status), the integrating developer (`detail`, field paths, docs link), the end user (not your job — give them structured data to localise), and you at 3am (`request_id`). RFC 9457 `problem+json`. [L10] |
| 57 | Why a `code` and not just a message? | Clients branch on whatever you give them. Give them prose and you can never reword it, i18n breaks them, and they write `msg.includes("expired")`. `code` is the contract; `detail` is courtesy. [L10] |
| 58 | Rule for how many error codes? | **One per distinct client action.** `token_expired` (refresh and retry) and `invalid_api_key` (stop) are both 401 but need different code paths, so they need different codes. Keep the total list finite and reviewable. [L10] |
| 59 | Upstream processor returns 500. What do you return? | `502 upstream_error` (or 504 on timeout) with your own `request_id`, never their raw body. **Then the real point: decide the state of the operation.** If you sent the charge and lost the response, money may have moved — so record the attempt against the idempotency key *before* calling out, and reconcile asynchronously. The ambiguity is worse than the error. [L10, L18] |
| 60 | Should an API accept an extra parameter? | Four asymmetries: **responses** — clients must ignore unknowns (or you can never add a field); **request bodies** — reject by default (a typo'd `currncy` silently charging in a default currency is worse than a 422, and strictness blocks mass assignment); **query params** — reject always (a typo'd filter returns the wrong dataset while looking successful); **round-trip `PUT`** — the one case for leniency. [L11] |
| 61 | What's a breaking change? | Removing/renaming anything, changing a type, adding a required field, adding a validation rule, changing a status code or error code for the same condition, changing a default, making a field nullable, narrowing an enum, changing pagination semantics — and worst of all, **changing a field's meaning without changing its shape**. [L11] |
| 62 | Is adding a response field breaking? | Non-breaking by contract, but Hyrum's Law says someone is doing strict validation or snapshot-testing responses. So: non-breaking, I'd still check usage and announce it, and I'd never add a field that changes the meaning of an existing one. [L11] |
| 63 | Is adding an enum value breaking? | For responses, effectively yes — clients with an exhaustive `switch` and no default break silently. Mitigate by documenting enums as **open** from day one and modelling them as open unions in typed clients. [L11] |
| 64 | Version an API for 5,000 integrators. | Frozen `/v1` path + date-based version pinned per account, with an internal chain of forward/backward transformers (Stripe's model). Be honest about the cost, then add: *"most of the effort goes upstream — making changes additive — because every version is permanent maintenance."* [L11] |
| 65 | Remove a field 200 clients might use. | Lead with **instrumentation** — per-client usage metrics, so you email the exact eleven accounts still calling it. Then expand/contract, `Deprecation`+`Sunset`+migration `Link`, an announced brownout (the only technique that reliably produces action), then removal. [L11] |

## Part 3 — Security (35)

| # | Question | Strong answer |
|---|---|---|
| 66 | Authn vs authz? | Who you are (401) vs what you may do (403). **Authorization is where APIs actually get breached** — OWASP API #1 is BOLA, not broken authentication. [L12] |
| 67 | Design API keys. | Public-id + secret split (O(1) indexed lookup instead of comparing every row), SHA-256 hash stored, identifiable prefix (`sk_live_`) for logs and secret scanners, `timingSafeEqual`, shown once, plus scopes, test/live separation, `last_used_at`, one-click revoke. [L12] |
| 68 | bcrypt an API key? | No. bcrypt/argon2 exist to slow brute force against **low-entropy human passwords**. A 256-bit random key can't be brute-forced, and bcrypt would add tens of ms to every request. SHA-256 is correct here — different threat model, different tool. [L12] |
| 69 | Is Basic auth secure? | Only as secure as its TLS — base64 is reversible in one line. Fine as an API-key transport (Stripe accepts it for `curl` ergonomics); never for a user's password on a public API. [L12] |
| 70 | How does a bank authenticate to your API? | **mTLS**, usually plus request signing, IP allowlists, and a certificate lifecycle. Why: no replayable bearer credential, identity proven at the transport layer, and PSD2/open-banking mandates it. [L12] |
| 71 | Three rules of HMAC request signing? | Sign `timestamp + raw body`; reject timestamps older than ~5 min (else replayable forever); constant-time compare, accepting multiple secrets during rotation. **And verify the raw bytes before parsing** — re-serialising changes key order and breaks the signature. [L12] |
| 72 | What's in a JWT? Encrypted? | Three base64url parts: header, payload, signature. **Signed, not encrypted** — the payload is readable by anyone holding it. Signature = integrity + origin, not confidentiality. (JWE encrypts; rarely used.) [L13] |
| 73 | Four attacks on naïve JWT verification? | `alg: none`; RS256→HS256 confusion (sign with the public key as an HMAC secret); `kid` injection (path traversal / SQLi / attacker-hosted JWKS); and using `decode` instead of `verify`. First two are stopped by one line: `algorithms: ["RS256"]`. [L13] |
| 74 | How do you revoke a JWT? | Never say "you can't." Four options: short expiry (5–15 min), a `jti` denylist in Redis with TTL, a per-user `tokens_invalid_before` timestamp (cheap, cached, handles "log out everywhere"), or full introspection. Any of them reintroduces a lookup — that's the honest cost. [L13] |
| 75 | HS256 or RS256? | Decided by *who verifies*. One service → HS256 fine. Multiple verifiers → RS256/ES256, because with HS256 every verifier holds the **signing** secret and can mint tokens. [L13] |
| 76 | Where do you store a token in a browser? | Not `localStorage` (XSS reads it). Access token in JS **memory**, refresh token in an `HttpOnly`, `Secure`, `SameSite` cookie scoped to the refresh path. Cookies are XSS-proof but need CSRF defence; the hybrid gets both. [L13] |
| 77 | Explain refresh token rotation. | Single-use refresh tokens; each use issues a new pair; a token presented **twice** means theft (or a race you can't distinguish from it), so revoke the whole token **family** and force re-auth. Mitigate genuine races with a ~10s grace window returning the same new pair, plus client-side single-flight. [L13] |
| 78 | Role changes admin→viewer. When does it apply? | With a 15-min JWT carrying `role`: up to 15 minutes later — often unacceptable for a privilege *reduction*. Options: keep authz data out of the token and look up per request, bump `tokens_invalid_before` on role change, or shorten the TTL. **Name the staleness window as a product decision.** [L13] |
| 79 | Why does OAuth exist? | So a user can grant a third party limited, revocable, attributable access without sharing their password. The password anti-pattern costs you five things: they hold the password, they get everything, no revocation without a password change, no MFA, and no per-app audit or limits. [L14] |
| 80 | Draw the auth code + PKCE flow. | The 10 steps — and narrate the three design questions: code-then-token because the redirect travels **in a URL** (history/`Referer`/logs); `state` for CSRF; PKCE for code interception. [L14] |
| 81 | What does PKCE prevent, exactly? | **Authorization code interception.** A public client has no secret, so the code alone suffices; on mobile another app could register the same custom URI scheme and steal it. PKCE binds the code to the client instance via `code_verifier`/`code_challenge` — **proof of possession**, and the verifier never leaves the device. Mandatory in OAuth 2.1 for all clients. [L14] |
| 82 | Why did implicit die? | The token itself travelled in the URL fragment (history, `Referer`, extensions), no client authentication or PKCE (token injection), and no refresh tokens (so long-lived access tokens). CORS removed the original justification. [L14] |
| 83 | OAuth vs OIDC? | OAuth = authorization: an **access token** for an API, opaque to the client. OIDC = authentication layered on top: an **ID token** (a JWT) for the client, validated by the client, triggered by the `openid` scope. [L14] |
| 84 | Why can't an access token authenticate a user? | It only proves *someone* granted *some* app access to *some* account — not which account, nor that the current user is it. So a token minted for another app can be replayed at your login endpoint. That's the confused-deputy / token-injection problem, and it's why OIDC binds the ID token to your `client_id` via `aud` and your request via `nonce`. [L14] |
| 85 | The #1 OAuth implementation bug? | Loose `redirect_uri` matching. Must be **exact** against a pre-registered allowlist — no wildcards, no prefix matching — or an open redirect leaks the code. [L14] |
| 86 | What is BOLA? | Broken object level authorization: an authenticated caller passes someone else's object ID and gets 200. OWASP API #1 because it needs zero sophistication, doesn't look like a bug in review, tests miss it (they're written as the owner), and every new endpoint is a fresh chance. [L15] |
| 87 | How do you prevent BOLA? | **Structurally**, not by vigilance: tenancy only from the credential; tenant as a required repository argument; per-request scoped repos so the unscoped call isn't in scope; Postgres RLS as a backstop; 404-not-403; and an actor×endpoint matrix in CI that **fails on uncovered routes**. *"I remove the ability to skip the check."* [L15] |
| 88 | UUIDs mean IDs can't be guessed — enough? | No. Unguessable IDs are defence in depth. IDs leak via exports, screenshots, support tickets, logs, misrouted webhooks and ex-employees. Authorization is the fix. [L15] |
| 89 | RBAC vs ABAC vs ReBAC? | RBAC: roles→permissions, simple and auditable, explodes combinatorially once conditions appear. ABAC: decisions from attributes, expressive but harder to audit. ReBAC: permission from a relationship graph (Zanzibar/SpiceDB/OpenFGA) for nested sharing. **Recommend RBAC as the coarse gate + an object-level policy function returning a reason.** [L15] |
| 90 | Where should authorization live? | Authn and coarse role/scope checks at the edge (cheap rejection). **Object-level authorization must live in the service** — a gateway doesn't know who owns `pi_3Nx8`. [L15] |
| 91 | Tenant isolation strategies? | Shared schema + `tenant_id` → + RLS → schema-per-tenant → DB-per-tenant → cells. Start shared + RLS; offer dedicated as a paid enterprise tier for residency/contractual requirements, because the cost curve only justifies isolation when the customer pays for it. [L15] |
| 92 | Mass assignment vs excessive data exposure? | Two directions of one failure: client writing fields it shouldn't vs server returning fields it shouldn't. Both fixed by explicit DTOs — `.strict()` input, **positive-allowlist** output. Never `delete obj.secret`: a deny list fails on the next column added. [L16] |
| 93 | Your mobile app hides the SSN in the UI. Fine? | No. If the API returned it, it's on the device and readable with a proxy in 30 seconds. Filter server-side. "The UI doesn't show it" is not a control. [L16] |
| 94 | What is SSRF and how do you prevent it? | Your server is tricked into fetching an attacker-chosen URL — typically cloud metadata (`169.254.169.254`) or internal services. **Cite Capital One (2019, 100M+ records).** Defence: protocol/port allowlist → resolve → validate the **IP** → connect to that IP with the `Host` header → `redirect: manual` with re-validation → **egress network controls + IMDSv2**. String blocklists fail on decimal/hex/IPv6 encodings, `nip.io`, redirects and DNS rebinding. [L16] |
| 95 | What's a financial DoS? | An unmetered endpoint that costs money downstream — SMS, email, AI tokens, image processing — is an attacker-controlled faucet on your bank account. Fix: per-tenant quotas, hard spend caps, alerting. Real companies have taken five-figure bills. [L16] |
| 96 | Business-flow abuse — an example where nothing is broken? | **Card testing:** an attacker validates stolen cards against your checkout. Every request is authenticated, authorized, valid and within rate limits — and you eat the gateway fees and processor risk score. Fix with per-merchant/per-fingerprint attempt limits, failure-ratio breakers, velocity checks, bot detection. [L16] |
| 97 | Improper inventory management? | *"We didn't know that endpoint was still live."* `api-v1.company.com` still running unpatched behind no WAF with production data. Fix: a generated API inventory, honour sunset dates, non-prod never holds prod data, and diff observed gateway routes against your OpenAPI spec to find undocumented endpoints. [L16] |
| 98 | Unsafe consumption of APIs? | You harden your endpoints then trust a partner's response blindly. Their data is untrusted input: validate the schema, bound the response size, set timeouts, never auto-follow their redirects into your network, and never use their URLs in a redirect. [L16] |
| 99 | Protect a login endpoint? | Per-IP **and** per-account limits with exponential backoff; never a permanent lockout (that's a DoS against your users); constant-work comparison with a dummy hash so timing doesn't reveal user existence; and a **global anomaly signal**, because credential stuffing uses one attempt per account across thousands and stays under every per-account limit. [L12, L19] |
| 100 | A key leaked to a public repo. Walk me through it. | Revoke immediately (don't assess first) → issue a replacement → **audit everything that key did**, which is only possible if you log `key_id` per request → notify the customer and compliance if data was touched → prevention: secret scanning in CI, push protection, prefixed keys, shorter-lived credentials. The forgotten step is the audit. [L12] |

## Part 4 — Production (35)

| # | Question | Strong answer |
|---|---|---|
| 101 | `no-cache` vs `no-store` vs `must-revalidate`? | `no-cache` = **store it, but revalidate before every use** (so you still get 304s). `no-store` = never write it anywhere. `must-revalidate` = once stale you may not serve it. Lead with *"no-cache doesn't mean don't cache."* [L17] |
| 102 | Can you cache an authenticated response? | Yes, in a **private** cache: `Cache-Control: private, no-cache` + `ETag` + `Vary: Authorization`. Fresh on every use, but a 304 costs ~150 bytes instead of the body. Most APIs use `no-store` here and throw that away. [L17] |
| 103 | How does a 304 work and what does it save? | Client sends `If-None-Match`; if the ETag matches you return 304 with **no body**. Saves the payload, the serialization, and — if you check the ETag before the read — the query too. [L17] |
| 104 | Cache stampede? | A hot key expires and N concurrent requests all miss and hit the origin, which falls over. Fixes: single-flight (one computes, the rest await), jittered TTLs, serve-stale-while-revalidating, pre-warming known-hot keys. [L17] |
| 105 | Cache penetration? | Requests for keys that don't exist always miss, so an attacker requesting random IDs turns your cache into a pass-through. Fix: cache the negative result with a short TTL; at extreme scale, a Bloom filter. [L17] |
| 106 | How do you invalidate a cache? | Say the honest thing first: it's the hard part, so default to short TTLs. When you need immediacy, use **key versioning** — bump a version counter on write so all derived keys become unreachable at once, rather than enumerating them. [L17] |
| 107 | Would you cache `GET /balance`? | No. Money must be exact; a stale balance costs more than the round trip saves. **Being able to decline to cache, with a reason, is as valuable as knowing how.** [L17] |
| 108 | Find and fix an N+1. | Detect it: log **query count per request** and alert above a threshold — a request whose query count scales with its result size is an N+1. Fix: collect the IDs, one `WHERE id = ANY($1)`, build a Map. Node has no lazy loading to save you. [L17] |
| 109 | What's the fastest possible API response? | The one you never send — a fresh cache hit, zero bytes on the network. [L17] |
| 110 | Client POSTs, times out, retries. Prevent a double charge. | The flagship. (1) Name the ambiguity — the client can't know, so it must retry. (2) `Idempotency-Key`, client-generated UUID, stable across retries. (3) Storage: key + **tenant** + endpoint + request hash + state + stored response, claimed atomically with `INSERT … ON CONFLICT`. (4) Four outcomes: execute / replay / 422 on a different body / 409 if in flight. (5) The details: 24h TTL, **5xx releases the key**, canonical body hashing. [L18] |
| 111 | Why can't the server just make POST idempotent automatically? | It can't distinguish a retry from a genuine second purchase — two identical "charge 4999" calls might be either. **Only the client knows**, so the key must come from the client. [L18] |
| 112 | Why must 5xx release the idempotency key? | A 500 might mean nothing happened, so the client must be able to retry. Caching the 500 against the key makes a transient blip a permanent failure for that operation. [L18] |
| 113 | Same key, different body? | `422 idempotency_key_reused`. Never guess: replaying the stored response would tell them "your 100 charge succeeded" when they asked for 5000, and executing the new body breaks the guarantee. [L18] |
| 114 | Does exactly-once delivery exist? | Not over a network — it's the Two Generals problem. What exists is **at-least-once delivery + idempotent processing = effectively once**. (Kafka's "exactly-once semantics" is real but narrower: atomic read-process-write *within* Kafka, not for external side effects like charging a card.) [L18] |
| 115 | Why full jitter and not backoff + a little randomness? | Because the failure mode is **synchronisation**. 5,000 clients failing at the same instant wake at ~200ms, ~400ms, ~800ms in coordinated waves that re-kill the recovering service. Full jitter — `random(0, cap)` — spreads them uniformly. [L18] |
| 116 | Retry amplification? | Nested retries multiply: 3 layers × 3 attempts = 27 requests at the bottom, arriving exactly when the bottom is already failing. Fixes: retry at one layer only, retry budgets (~10% of traffic), circuit breakers. [L18] |
| 117 | What does a circuit breaker buy you? | **Failing fast.** Without it, every doomed request waits the full timeout — at 100 rps with a 10s timeout that's 1,000 requests parked in your process. It protects **you** from your dependency. Refine with a failure *ratio* over a window, don't count 4xx, and jitter the cooldown. [L18] |
| 118 | What's a bulkhead? | A per-dependency concurrency cap, so a slow unimportant dependency can't consume every worker and take down an important endpoint. Named for ship compartments. [L18] |
| 119 | Why shed load instead of queueing? | An unbounded queue converts a capacity problem into a **total** outage: every request times out, every timeout triggers a retry, retries add load. Fast `503` + `Retry-After` keeps you partially available. [L18] |
| 120 | You write to the DB then publish an event and crash in between. | The dual-write problem. **Transactional outbox**: write the event row in the same DB transaction, then a worker publishes and marks it sent. At-least-once, so consumers must be idempotent. [L18] |
| 121 | Processor starts taking 30s. What fails, in order? | Requests pile up → your pool saturates → **unrelated endpoints** start timing out → clients retry, doubling load → health checks fail and the orchestrator restarts pods, dropping in-flight work → restarts empty caches so recovery is slower. Fixes mapped: timeouts, bulkhead, breaker, load shedding, and **health checks that don't depend on the downstream**. [L18, L20] |
| 122 | Timeout ordering? | Decreasing downstream: client 30s > gateway 25s > service 20s > processor 10s > DB 3s > Redis 200ms. Otherwise you hold resources doing work nobody awaits. Propagate a **deadline** so downstreams can refuse work they can't finish. [L18] |
| 123 | Five rate-limit algorithms? | Fixed window (cheap, **2× boundary burst**); sliding log (exact, memory scales with traffic); sliding counter (approximate, no boundary burst — Cloudflare); **token bucket** (burst + sustained in two parameters — AWS/Stripe, my default); leaky bucket (delays rather than rejects). [L19] |
| 124 | Why token bucket by default? | Real clients are bursty — a dashboard fires 8 parallel requests, a nightly sync fires 200 then sleeps. A strict per-second limiter rejects a legitimate page load. Token bucket expresses "10/s sustained, 100 burst", which is what you actually mean. [L19] |
| 125 | 10 instances, one global limit? | Shared atomic state — Redis with a **Lua script**, because read-refill-write must be atomic and Lua runs as one server-side operation. If the hop is too costly, per-instance buckets at `global/N` with reconciliation, accepting the approximation. [L19] |
| 126 | What if Redis is down? | A deliberate choice: **fail open** for normal endpoints (a limiter outage shouldn't be an API outage), with a metric and an alert; **fail closed** or fall back to a local limiter on `/auth/*`, where failing open means unlimited brute force. [L19] |
| 127 | Why not rate limit by IP? | Shared IPs (corporate NAT, mobile carriers) mean thousands of users share a budget, and IPs are cheap to rotate. IP only for anonymous traffic; prefer a stable identity. And **never trust `X-Forwarded-For`** unless your own proxy set it. [L19] |
| 128 | Rate limit a bulk endpoint? | Per **item**, not per request — otherwise 100-item batches multiply the quota by 100. Same for GraphQL: limit on complexity, not request count. [L19, L21] |
| 129 | The 429 contract? | `Retry-After` (mandatory), `RateLimit-Limit/Remaining/Reset`, a `problem+json` body naming the `scope` that fired, and **`RateLimit-*` on every response, not just 429s** — a client that can see its budget self-throttles and never hits the limiter. Don't count 429s against the limit. [L19] |
| 130 | Rate limiting vs DDoS protection? | Different layers, different goals. Rate limiting is application-layer fairness and cost control, keyed on identity. DDoS protection is network/edge volumetric absorption — by the time a flood reaches your app, defending it is already too expensive. [L19] |
| 131 | Monitoring vs observability? | Monitoring answers pre-defined questions; observability lets you ask new ones without shipping code. The enabler is high-cardinality context on logs and traces, tied together by one ID. [L20] |
| 132 | Why not averages? | An average of 200ms fits "everyone gets 200ms" and "90% get 20ms, 10% get 2s" — only the second is an incident. Use histograms and percentiles. And percentiles can't be averaged across instances; you aggregate buckets. [L20] |
| 133 | Cardinality — what and why? | Each unique label combination is a time series. An ID label creates one per entity — millions — which kills your metrics store and your bill. **Bounded labels on metrics** (route patterns, never raw URLs); high-cardinality detail on traces and logs. [L20] |
| 134 | Should a health check verify the database? | **Readiness yes, liveness no.** A DB blip fails every liveness probe, Kubernetes restarts the whole fleet, and a 30-second blip becomes a 10-minute cold-start outage. Also: readiness must fail *first* during graceful shutdown so the LB drains you. [L20] |
| 135 | p99 spiked to 4s, p50 flat at 40ms. Investigate. | The method, not a guess: who (per-client p99) → where (split DNS/TCP/TLS/server-think/transfer) → which endpoint → when (deploy? cron? traffic?) → inside (open a slow trace: downstream? DB query count? event loop? queue wait?) → then find the metric that would **disprove** your hypothesis. And *"if p99 ≈ exactly my timeout, I'm measuring the timeout, not the work."* [L20] |

## Part 5 — Beyond REST & craft (30)

| # | Question | Strong answer |
|---|---|---|
| 136 | What problem does GraphQL solve? | Over-fetching and the client-side N+1 (61 requests for a 20-row table) — and more importantly, **decoupling front-end iteration from backend deploys** when several clients evolve independently over a deep graph. REST can solve both, but with a bespoke endpoint per client need. [L21] |
| 137 | What does GraphQL take away? | HTTP caching, per-endpoint rate limits, per-endpoint metrics, meaningful status codes, predictable query cost, `curl`-ability, and per-endpoint authorization (it moves to every field). None fatal; **all of them work you must budget for.** [L21] |
| 138 | When would you NOT use GraphQL? | Public third-party APIs (REST is expected, cacheable, curl-able — and you'd expose unbounded query cost to strangers); simple CRUD with one client; when HTTP caching or CDN offload is a requirement; file uploads and binary streaming; high-volume service-to-service (gRPC); and when the team can't fund the operational work. [L21] |
| 139 | Stop an expensive GraphQL query? | Depth limit **and** complexity scoring — depth alone misses `first: 1000` breadth. Plus query timeouts, max query bytes, alias caps, disabled array batching, and **persisted queries as an allowlist** for first-party clients. Rate limit on complexity, not requests. [L21] |
| 140 | Why is GraphQL caching hard? | One `POST` URL with body-dependent responses, so URL-keyed caches can't help. Solutions: normalised client-side caching by object ID, **persisted queries over `GET`** (a hash makes a cache key — this gets your CDN back), and resolver-level server caching. [L21] |
| 141 | GraphQL N+1 and DataLoader? | In REST an N+1 is a bug you can see; in GraphQL it's the **execution model** — resolvers genuinely run per object. DataLoader batches within a tick. Two rules: **one instance per request** (a global loader leaks across tenants) and the batch function must return results in key order. [L21] |
| 142 | Everything returns 200 — impact? | Monitoring reads 0% errors during incidents; retry logic and LBs see success; every client must inspect `body.errors`. Mitigate with explicit error metrics keyed by `extensions.code`, and model expected domain failures as **union result types** so `errors` means "something genuinely broke". [L21] |
| 143 | Version a GraphQL API? | You don't. Add fields, `@deprecated(reason:)` old ones, and use **field-level usage metrics** to know when zero clients read a field, then remove it. The metrics part is what people forget. [L21] |
| 144 | The non-null cascade? | If `Payment.customer` is `Customer!` and its resolver errors, GraphQL can't null it, so it nulls the **parent** — and if the list is `[Payment!]!`, the whole list. One failing sub-field blanks the screen. Hence: nullable by default, `!` deliberately. [L21] |
| 145 | Why is Protobuf smaller and faster? | Field **numbers** instead of names on the wire, varint encoding for small integers, and no text parsing — plus a mandatory schema, so the parser knows the shape in advance. [L22] |
| 146 | What happens if you change a Protobuf field number? | Silent data corruption: the old number becomes unrecognised and the new one may collide with a previous meaning. Always `reserved` removed numbers **and** names. [L22] |
| 147 | Why can't browsers use gRPC? | The final status arrives in **HTTP trailers**, and the Fetch API exposes neither trailers nor HTTP/2 framing control. Hence grpc-web (with a proxy, no client streaming), Connect, or a REST gateway. [L22] |
| 148 | What does gRPC give you free? | Deadlines propagated automatically, declarative retry policy and backoff via `service_config`, generated clients in 10+ languages, four streaming modes, and mTLS via a mesh. **It does not give you idempotency** — it can't know whether your method is safe to repeat. [L22] |
| 149 | How do you load balance gRPC? | The gotcha: long-lived multiplexed connections mean a naïve L4 balancer pins all a client's traffic to one backend, so replicas don't help. Use client-side load balancing, a mesh sidecar, or an L7 proxy that balances individual HTTP/2 streams. [L22] |
| 150 | Serve both external REST and internal gRPC? | One `.proto` as the source of truth with `google.api.http` annotations, and `grpc-gateway` (or Connect) generating the REST façade. One contract, two protocols, no drift. [L22] |
| 151 | Notify a client that a long job finished? | Ask **who the client is.** Browser → SSE (or poll a job resource). Another company's server → webhook. Your own service → a queue. REST shape: `POST /jobs` → 202 + `Location` → poll or callback. [L23] |
| 152 | SSE vs WebSocket? | SSE: one-way, plain HTTP, **automatic reconnect with `Last-Event-ID` resume**, existing auth/proxies/tracing work, text only, needs HTTP/2 (HTTP/1.1's 6-connection limit deadlocks tabs). WebSocket: bidirectional, binary, but you hand-write reconnection, auth, heartbeats and backpressure, plus sticky routing and pub/sub to scale. **Default to SSE.** [L23] |
| 153 | How do you authenticate a WebSocket? | Not with a header — the browser API can't set them. Auth-by-first-message with a close-on-timeout, or a short-lived single-use ticket from a REST call. **And validate `Origin`**, because CORS doesn't apply to the handshake but cookies are sent (cross-site WebSocket hijacking). [L23] |
| 154 | 500k concurrent WebSockets — what breaks? | Memory and file descriptors per connection; sockets pinned to instances so a deploy drops all of them and the reconnect storm self-DDoSes (fix: jittered backoff); fan-out needs pub/sub; slow clients back up in server memory (`bufferedAmount`); health checks must not count a busy pump as unhealthy. [L23] |
| 155 | Design a webhook system. | Outbox in the same transaction → dispatcher fan-out per endpoint → worker pool with short timeouts → HMAC over `timestamp.rawBody` → jittered exponential backoff, ~8 attempts / ~3 days → dead-letter + auto-disable + notify → delivery log with manual retry → **a pollable event log as the fallback** → and the honest statements: ordering not guaranteed, duplicates guaranteed. [L23] |
| 156 | Can webhooks be ordered? | No — retries reorder them by construction. Options: document it and ship a `sequence` (what everyone does); serial delivery per endpoint (guarantees order, but one stuck event becomes a multi-day backlog); or per-entity ordering. Tell receivers to treat a webhook as a signal to **read current state**. [L23] |
| 157 | Merchant's endpoint is down 6 hours. What happens? | Retries follow the published schedule; after the cap, deliveries dead-letter, the endpoint is disabled, the merchant is emailed. **No events are lost** — they're all in the event log, so the merchant reconciles via `GET /v1/events?after=` or replays specific deliveries. [L23] |
| 158 | Isn't polling bad? | Often it's correct: stateless, trivially scaled, works through every proxy, no reconnection logic, easy to debug — and with `ETag`/304 an empty poll is ~150 bytes. The argument against it is arithmetic (10k clients × 0.5 Hz = 5k rps). Measure before adding push. [L23] |
| 159 | REST or GraphQL or gRPC — which is best? | Refuse the premise and name the deciding constraints: client profile, domain shape, volume, and team capacity. Then commit for *their* scenario. Never answer with a favourite. [L24] |
| 160 | Is REST dead? | No — ~80% of public web APIs. What changed is it's no longer the only answer: gRPC took internal traffic, GraphQL took client-flexible products, REST kept the edge. Boring and universally understood is a **feature** for a public contract. [L24] |
| 161 | Is SOAP dead? | No, and this is a trap for modern-only engineers. Load-bearing in banking, insurance, healthcare, government — because it standardised **message-level security that survives TLS termination** and formal transactions. Wrap it, don't propagate it, and don't argue with a counterparty's mandate. [L24] |
| 162 | When is tRPC right? | A TypeScript monorepo where client and server ship together. It works by importing server **types**, so: TS-only both ends, no independent contract, and versions must move together. Structurally unsuited to a public API. [L24] |
| 163 | What would change a style decision? | Name concrete triggers: 3+ round trips per screen and rising → `?expand=`, then GraphQL for the first-party client. JSON parsing in CPU profiles → gRPC on the hot path. Clients polling >4×/min → SSE. A third party needing guaranteed delivery → webhooks + event log. **Naming triggers is the strongest thing you can add.** [L24] |
| 164 | How do you keep docs in sync with code? | Don't sync them — **make them the same artifact**. Generate the spec from code, or generate/validate code against the spec. The mechanism: `validateResponses` in CI, so a handler returning an undocumented field fails the build. A hand-maintained spec next to hand-written code is the one configuration guaranteed to drift. [L25] |
| 165 | What do you generate from OpenAPI? | Types, a typed client, request validation, **response validation**, mocks (so the front end starts day 1, including error paths), docs, contract tests, and **`oasdiff breaking`** as a CI gate. The last two are what distinguish a real answer. [L25] |
| 166 | What can OpenAPI *not* express? | Semantics (units, meaning, inclusivity), cross-field validation rules, state machines (which transitions are legal), operational guarantees (consistency, ordering, delivery), and workflow sequencing. Those live in prose and your error contract — which is why layer 2 can never be fully generated. [L25] |
| 167 | How do you test an API? | Invert the usual pyramid slightly: **heavy on integration tests against a real DB via real HTTP**, because API bugs live in the seams (middleware order, tenancy, transactions, serialization). Unit for pure logic. Contract tests against OpenAPI. A few E2E. Then the four property tests: idempotency, concurrency, authorization matrix, transaction integrity. [L26] |
| 168 | What do most API test suites miss? | Concurrency, idempotency, **negative** authorization tests, boundary values, documented error paths, and behaviour under downstream failure. *"Teams test that Alice can read her payment; almost nobody tests that Bob can't."* [L26] |
| 169 | How do you test a race condition? | `Promise.all` of N identical requests, assert on the **effect** (exactly one row; statuses `[201, 409]`), and repeat it 20× in CI — races are probabilistic and one pass proves nothing. Add artificial latency to widen the window. [L26] |
| 170 | Consumer-driven contract testing — when? | Consumers publish pacts; the provider's CI verifies it satisfies all of them, so you learn which client a change breaks at build time. Worth it with several coordinatable internal consumers; useless for a public API with unknown integrators — there use OpenAPI + `oasdiff` + per-client usage instrumentation. [L26] |

## Part 6 — Judgement & senior signals (10)

These have no single right answer. They test whether you think in trade-offs.

| # | Question | What a strong answer contains |
|---|---|---|
| 171 | What makes a good API? | Predictable, consistent, minimal, hard to misuse, honest about failure, observable, evolvable, documented at the semantic level. Then the best heuristic: **write the client code first** — if the five lines a consumer wants need three round trips and a `setTimeout`, the design is wrong. [L01, L27] |
| 172 | What's the hardest part of API design? | **You can't take anything back.** Naming, semantics and defaults are permanent the moment a third party ships against them — which is why contract-first review exists and why "we'll clean it up later" isn't available. [L01] |
| 173 | What would you change about an API you built? | A real trade-off you'd revisit, with the mechanism: *"we returned entities directly to move fast and within a year had published four internal fields we couldn't remove. DTOs cost an hour; removal cost a deprecation cycle."* Specific, self-aware, mechanism-level. [L27] |
| 174 | 15 minutes to review a 5,000-line API PR? | Prioritise, don't read linearly: route list → every query (tenancy) → every input schema (strictness) → every outbound call (timeouts) → error paths → tests, checking specifically for authorization and concurrency coverage. And say that **the diff you skip is the diff you trust the tests to cover** — which is why the authz matrix meta-test matters. [L27] |
| 175 | How do you give feedback someone acts on? | Severity → what → the **concrete consequence** → a suggested fix, with preferences marked as preferences. *"A review that buries a missing authorization check under twelve naming nits has failed."* [L27] |
| 176 | Internal APIs — do they need the same rigour? | *"Not if you genuinely know every consumer and can coordinate deploys. That holds at 5 services and fails at 50 — nobody knows who calls what, so big companies end up treating internal APIs like public ones. I'd skip formal versioning early but keep the additive discipline from day one, because the discipline is what makes versioning unnecessary."* [L11] |
| 177 | You're told your documented non-breaking change broke a client. | Roll back or ship a compat shim **first** — their outage outranks being right. Then find what they depended on (usually strict validation, key order, or a field's absence), document it explicitly, and add a contract test. **Never lead with "you were doing it wrong."** [L11] |
| 178 | Critical vulnerability in production — the next hour? | **Contain** (revoke / disable the endpoint / WAF rule) → assess blast radius from logs → fix → verify → notify (customers; legal/compliance if data was touched — GDPR is 72h) → post-mortem with a systemic fix **and a regression test**. Containment before root-cause analysis. [L16] |
| 179 | Your team wants to rewrite the API. Talk me through it. | Strangler fig, never big-bang: new surface alongside the old, migrate consumers endpoint by endpoint with **instrumented per-client usage**, keep the old running, retire when usage is zero. And fix the domain model as you go, or you've just re-shaped the same bad contract. [L11, L24] |
| 180 | What does the API style choice *not* fix? | A badly-modelled domain, missing authorization, absent idempotency, no observability, an unversioned contract. **All style-independent, and all matter more than the style.** Ending an architecture answer here is memorable. [L24] |

From [the API README](../README.md). Give yourself 2 minutes each, out loud, no notes. Score honestly.

1. Safe vs idempotent vs cacheable — with a method that's one but not the others

6. Why `?page=40000` is broken and what replaces it
7. `no-cache` vs `no-store` vs `private` vs `must-revalidate`
8. What a CORS preflight checks and why the browser does it
9. Where to store a JWT in a browser, and the attack each option exposes
10. How to revoke a JWT, and what you gave up by needing to
